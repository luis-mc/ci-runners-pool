Research summary

Limit: the session could open no product site (network blocked), so these points come from search result summaries, not from reading each page in full. Quotes are short. Check any point before relying on it.

ProductWhat I foundWhat it means for crsp
BuildkiteCluster insights show queue wait time, jobs waiting and agent use, with p50 to p95 breakdowns. A queue page shows wait time that "begins when a job becomes runnable". There is also a build waterfall. Sources: Buildkite: queue metrics, Buildkite: cluster insights, Buildkite: waterfall view.Wait time is a first-class number, split from run time. Percentiles are for trends, not for one job.
SlurmEvery pending job carries a reason code ("Priority", "Resources" and others), and a job can have more than one. Backfill lets a lower-priority job start only if it does not delay the top job. Sources: Slurm: job reason codes, Purdue: why is my job waiting. One admin thread found jobs pending as Priority while nodes were idle, because a time request clashed with a reserved start: Slurm users: pending with "Priority" while idle.The model closest to crsp (reservation + backfill). Its lesson: show the rule, not only the word.
NomadPlacement failures name the exhausted dimension and how many nodes it hit, for example CPU or memory. A blocked evaluation waits for capacity. Sources: Nomad: eval status, Nomad: inspect jobs.A per-machine "why not here" list is normal practice.
Kubernetes and LensA Pending pod has a FailedScheduling event such as "0/2 nodes are available: 1 Insufficient cpu". The scheduler counts requests, not live usage. Sources: Datadog: debug Kubernetes pending pods, Kubernetes: assign CPU resources. I found nothing on Lens specifically.Show what is reserved against the pool, not only the live load.
GitHub Actions and ARCPerformance metrics show run time, queue time and failures, and can filter by runner label. ARC exposes assigned, running, busy and idle counts; min runners now means minimum idle. Sources: GitHub: Actions metrics, GitHub changelog: metrics by runner label, ARC: runner scale set metrics issue, GitHub: deploy runner scale sets.GitHub itself gives no per-job reason for waiting on a self-hosted runner. crsp can fill that gap.
CircleCIInsights show credits, success rate and duration; resource class insights show historical CPU and RAM per job, up to 24 h late. Sources: CircleCI: Insights, CircleCI: resource class insights.Measured peaks per job feed sizing. That matches crsp "measured" sizes.
Datadog CI VisibilityQueue time is a column next to run time; the critical path is the longest chain of jobs, and queue time on it is reported. Sources: Datadog: CI pipelines, Datadog: critical path. I could not confirm the name of its timeline view.Queue time on the critical path is what users feel.
GitLabA pending job shows "stuck" text, with causes like tag mismatch. Reports include a runner shown idle while the job stays pending. Source: GitLab forum: job is stuck, no active runners.Shows what a vague reason costs. A tag mismatch is the same case as a crsp label with no carrier.
GrafanaThreshold lines belong on time series panels; stat panels colour the value. Source: Grafana: configure thresholds.Supports the dashed pool line on the step charts.
Docs patternsDiátaxis separates tutorials, how-to, reference and explanation; concept pages explain and link to reference; a glossary is the source of canonical terms. Sources: Diátaxis, Diátaxis: complex hierarchies. Evidence on in-context help was thin in my searches.Help sections should be explanations, with the glossary and reason table as reference.

Practices that came out of it

  • Reason on the waiting item, in words, with a code for support (Slurm, Kubernetes, Nomad).
  • Capacity as reserved against a limit, with the limit drawn as a line (Kubernetes requests, Grafana threshold lines).
  • Waiting and running are different colours on a timeline (Buildkite, Datadog).
  • Explanations separate from reference: concept pages plus a glossary and reason table (Diátaxis).

Hypotheses

HypothesisResultEvidence and check against the console
H1A user's first question is "why is my job waiting?", not "how busy is the pool?"HeldSlurm, Kubernetes, Nomad and GitLab all put a reason on the pending item. The Jobs screen already has a Queue pane with a "Why it waits" column, but it still says "slot" and shows no machine, no expected start and no rule. Overview shows load bars only.
H2Capacity should show what is reserved (job size against the pool), with live load second.HeldKubernetes schedules on requests, and crsp admits on job size. A pool can be full while load is low. All charts here sum job sizes. Load budget stays as the pool edge.
H3A per-job timeline that splits waiting from running is the best single picture.Partly heldBuildkite (waterfall) and Datadog (queue time on the critical path) support it for one run. Their aggregates are percentiles, which suit history, not "now". The Gantt is best for now plus forecast; trends belong to Jobs insights.
H4A forecast start is trusted only when its rule and assumption are visible.Held (thin evidence)Slurm users hit surprise Priority waits caused by time limits. This rests on one thread plus the reason-code docs, so check it with real users. Every option shows the rule (reservation, backfill, timers) beside the time.
H5Concept help works best when linked from the place where the term appears.Not confirmedDiátaxis supports separate explanation pages, but my searches found little on in-context help. Options B, C and E test it by linking "Learn" from the screens.

Checks against the console were made from the code (apps/web/src/screens) and a render of Overview, not from user tests. All five need a user check.

A A new Pool tab with Live, Plan, Labels and Timers

One new place for the whole picture.

Key states

Help in this option

Tab row of 11 sections with static pictures and "See it live in Pool".

What it shows

Live: counts, the timer alert, the Gantt, three machine step charts. Plan: queued jobs with reason, start, machine, runner, plus the reservation. Labels: the routing table. Timers: every running job with its timers and the grace card with Stop now and Extend 10 min.

Covers: (a) at a glance, (b) the plan, (c) running jobs and timers with the grace state, (d) labels, (e) Help sections.

Pros

  • Everything about "now" in one place, one navigation step.
  • Gantt and capacity share one time axis.
  • Easy to explain and to test.

Cons

  • A new top-level tab on a nav that is already full (UX-1, UX-14).
  • Jobs, Machines and Overview now overlap with it (UX-2).
  • The Live tab is long on a phone.

Effort

Large: about 5 new parts, a route, and the data feed for forecasts.

C An Execution plan screen built on reason codes

Answer "why is it waiting" first.

Key states

Help in this option

Starts from "Why is my job waiting?" and links to the four concepts behind the reasons.

What it shows

A queue in start order. Each job: reason in words and a code, needed against free CPU and memory, the fix, size source, label, planned machine and time. Reservation with the starvation versus reserved chart. Running jobs and timers. A filter by reason. A job at risk of the run timer.

Covers: (a) at a glance, (b) the plan, (c) running jobs and timers with the grace state, (d) labels, (e) Help sections. Part (a) is thin: no machine view.

Pros

Cons

  • A second queue next to Jobs, so users may not know which to open (UX-1).
  • Reason words need new content entries.

E A "why waiting" inspector on every job row

Explain one job at a time, where you see it.

Key states

Tab row; each inspector Learn link opens one section.

What it shows

Jobs list with a side inspector: reason and fix, a "why not each machine" table, needs, size source, label, plan, the job on the timeline, timers, and a Learn link. Shown for room, reserved, no runner and timer ran out (with Stop now and Extend 10 min).

Recommendation

Build C and F first, with the Gantt from A as the Jobs page's timeline view; skip a new top tab.

  1. C (Execution plan by reason) answers the first question users ask (H1) and shows the rule behind each forecast (H4). It is also the cheapest way to show reservation and backfill honestly.
  2. F (live Help) moves "how it works" out of the screens, as asked, and its pictures reuse the parts C needs.
  3. Add the Gantt (A) as one more view of Jobs, not as a new tab. It is the chart the owner liked, and it covers "where running jobs are going". A new Pool tab (A) overlaps Jobs, Machines and Overview, and the nav is already full.
  4. Then B's machine strip on Machines (cheap), and a link-only version of D for Overview (UX-52).
  5. Defer E. The inspector is the best explanation per job, but it needs a new overlay rule first. Its "why not each machine" table could move into C's rows now.

Open questions for the owner: should the plan show times as clock times only (UX-18), and may a job at risk of the run timer be shown as "Needs you"? Forecast quality matters more than layout here: if estimates are poor, show "about" and the assumption, or hide the time.
