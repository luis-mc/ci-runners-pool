Persistent or ephemeral is the user's choice, persistent runners are always cleaned, and the pool takes ephemeral runners for every repository (R5.1, R5.47, R5.88, R5.90 to R5.93). Reasoning (owner decisions D93, D94, D95, 18 Nov 2026): D93 wants the kind chosen when runners are added, so Add runners step 1 offers only the kinds the machine can run and says why a kind is not offered, and refusals come back at plan time. D94(b) preselects Ephemeral while a public repository uses the pool. The controller no longer refuses an ephemeral pool request: it is a ceiling of ephemeral runners at once per machine, each runner a fresh container per job from a JIT config, all carrying the label `ephemeral` that no persistent runner has (this is how the per-repository kind of github-integration R5.60 works with no scheduler change). A persistent Linux runner on a Windows machine, refused until now, is a long-lived container after the dev-standards runner pool model (supervisor with back-off, `config.sh --unattended --replace`, clean hooks, tool cache in a volume). D95: the job's temporary files (the `_work` workspace, the runner account's temp folder, `/tmp` entries of the runner user, processes the job left) are always removed after every job and before the next, on every persistent runner, and this is not a setting: a leftover can leak a secret or a half-built tree into the next job, possibly another repository's, so a failed cleanup marks the runner unclean and it takes no job. Only downloaded dependencies (tool cache, package manager caches, Playwright browsers, Docker layers) are a per-runner choice, Keep downloaded dependencies, on by default, kept in the runner's own folder and never shared. The clean-up decides in `internal/hooks` which files and processes are left over; `internal/runnerprocs` is the one package that lists and ends processes, so the hook package keeps its no-exec rule (hooks R5.62) and the scheduler guard (scheduling R5.27) stays whole.
